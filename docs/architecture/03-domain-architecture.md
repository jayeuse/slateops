# Domain Architecture

> **Scope:** Business capabilities and their durable boundaries.

Slate Operations groups domain behavior under FastAPI `systems` packages:

| Area | Responsibilities |
| --- | --- |
| `access` | Supabase Auth identity binding, application users, roles, groups, group-access policy, invitations, and recovery |
| `sandbox` | Shared design draft/history, safe publication, departments, modules, fields, records, relationships, lifecycle, temporary tests, and record trigger execution |
| `openview` | Department dashboards, shared saved views and charts, reports, frozen report runs and schedules |
| `boards` | The company Board, one Board for each department, project Boards and their groups; posts with their published revisions, events with author-set reminders, attachments and record links |
| `manage` | Workspace profile, audit history, backups, and administrator job monitoring |
| `platform` | Private files and department libraries, SSE invalidations, scheduled work, and in-app notifications |

User profiles and their role values are application-owned in the [user model](../../backend/app/systems/access/users/models.py). Supabase Auth owns password credentials and email-action tokens; a provider subject must be explicitly bound to an eligible Slate Operations profile before it can start an application session. Slate Operations keeps revocable [`IdentitySession`](../../backend/app/systems/access/identity/models.py) rows and rate-limit buckets in its own PostgreSQL schema. Each session binds the provider user and session IDs, stores a digest of its opaque refresh handle, and retains the encrypted current provider token pair. [`effective_levels`](../../backend/app/systems/access/policy/scope.py) resolves access from current account eligibility, role, and group-access rows: module rows override that group's department row, the highest level across groups wins, and a guest is limited to `read`. See [data architecture](06-data-architecture.md#identity-and-files) and [authentication and authorization](08-authentication-authorization.md).

Files have application metadata in the [file model](../../backend/app/systems/platform/files/models.py), an opaque object key, a lifecycle state, and nullable `enc_version`. Bytes stay in the private Supabase Storage `slateops-ready` bucket through the [Storage adapter](../../backend/app/systems/platform/files/supabase_storage.py). FastAPI mediates access; metadata alone never makes bytes readable. The [file service](../../backend/app/systems/platform/files/service.py) validates the file type, writes the bytes, and marks the file `ready` in the same upload request; download is denied in every other state.

Department library files use `purpose = 'library_document'` and a required `department_id`, without a Record or Board parent. [`authorize_action`](../../backend/app/systems/platform/files/access.py) requires the direct department level: `read` for listing/download, `write` for upload, and `manage` for archive/reopen. Module-only access does not grant department-library access. The library is not a public Storage browser.

The Sandbox publish is the only way to create or change departments, modules, and fields. A published module accepts new records while it has at least one active field; there is no separate schema acceptance step.

A department that a publish creates open gets its derived set in the same transaction: the groups "<Department> managers", "<Department> members" and "<Department> viewers", each with one department access row (`manage`, `write`, `read`) and no members; an empty home dashboard "<Department> dashboard"; and an OpenComms category and department channel with the department's name. The draft department's optional `setup` (`groups`, `dashboard`, `category`, `channel`, each on when missing) clears items before that first publish: a cleared category leaves the channel in no category, a cleared channel leaves the category empty, and the Board is always created; a later publish ignores `setup`. Existing, reopened, and closed-at-creation departments derive nothing. Each system creates its item through its own no-commit helper, and a `sandbox_derived_objects` row links each item to its department ([`derived/planning.py`](../../backend/app/systems/sandbox/derived/planning.py)). The review lists every derived change, including each department Board the Board loop changes, as `group`, `dashboard`, `board`, `category` and `channel` changes, and a derived group name that an active group or another new department already uses (ignoring case) blocks the publish with `derived_name_unavailable`. One pure function computes these changes for the review and the publish ([`derived/actions.py`](../../backend/app/systems/sandbox/derived/actions.py)); the executor refuses a publish whose created items differ from the reviewed ones. Every publish takes the OpenComms projection lock after the password check.

After creation, a linked item follows only its department's name and open or closed state, on both the publish path and the lifecycle close and reopen actions; one function applies the follow-up on both paths ([`derived/sync.py`](../../backend/app/systems/sandbox/derived/sync.py)). The sync finds items through their link rows, never by name, and changes nothing else: members, access rows, widgets, messages, and grants stay. Only a publish that renames the department writes the derived names, so a person's rename of an item lasts until the next department rename; renamed derived group names count in the `derived_name_unavailable` check, and a swap of two department names publishes. A close archives the derived channel (other channels, the groups, the dashboard, and the category keep their state) and records the close on every link row; a reopen unarchives the channel only when the close archived it and nobody archived or restored it since. The sync leaves alone an item a person removed (a deleted group, an archived dashboard, an archived or deleted channel) and a category or channel a person moved to another department. A publish that closes or reopens any department revokes stale OpenComms Realtime grants before its commit. The lifecycle close preview and every lifecycle result list these changes in `impact.derived_changes`: the channel's archive (`close`) or unarchive (`reopen`), and on a close each other open channel of the department (`keep`), which stays postable for administrators and grant holders; the impact digest covers the list ([`lifecycle/derived_changes.py`](../../backend/app/systems/sandbox/lifecycle/derived_changes.py)). A department purge deletes its link rows, and any OpenComms category or channel that references the department blocks the purge with `comms_department_content`.

A relationship field links records of its source module to records of one target module. The two modules can be in the same department or in two different active departments. To create, replace, or remove a link, a user needs `write` on the source module and `read` on the target module; a target the user cannot read is reported as missing (404). A user sees a link only when they can read both modules, and hidden links add nothing to lists or counts ([`relationships/access.py`](../../backend/app/systems/sandbox/relationships/access.py)). Lifecycle applies the same rules in both cases: close and reopen change no link rows, a purge removes the links of the purged rows, and a relationship field outside the purge that targets a purged module blocks the purge.

Server-backed OpenView content belongs to departments and modules. Dashboards, widgets, saved views, and Reports have no persisted per-person or role audience: their readers come from department or module access. Browser-local sample controls do not grant access. A Report run stores the module readers eligible when it is captured; reading its output also requires current module access ([`capture_run_eligible_users`](../../backend/app/systems/openview/reports/eligibility.py), [`run_reader_router.py`](../../backend/app/systems/openview/reports/run_reader_router.py)):

1. A dashboard belongs to one department and has a `position` in it. A user who can read something in an open department reads its dashboards. Only `manage` on the department, or an administrator, creates, changes or archives a dashboard. A closed department's dashboards are read and changed by administrators only (`openview/dashboards/router.py` `_dashboard_departments`). Each widget must read a module of the dashboard's department.
2. A saved view and a report belong to one module, and so to its department. Every user who can read the module reads them. Only `manage` on the module creates, changes or deletes them, and sets report schedules. One active view of each module can be its default; making a view the default clears the previous default in the same transaction.
3. Any non-guest reader of the module runs a report on demand, and the run keeps that user as its actor. A scheduled run acts as the workspace: its audit entries have no user in `performed_by` and carry `actor_label = "Scheduled report: <name>"` ([`platform/scheduling/execution.py`](../../backend/app/systems/platform/scheduling/execution.py)); it keeps running after every user who edited the Report is disabled.
4. The module readers at run capture are stored as the run's eligible readers. Output requests check both that captured eligibility and current module read access, so a user who loses access cannot open an earlier run.
5. A [saved chart](../../backend/app/systems/openview/charts/models.py) is a revisioned definition for one source module, with its department derived from that source. Reading it requires `read` on the source module. Creating, editing, archiving and restoring it require `manage` on the chart's department plus `read` on its source module; module-level `manage` alone is insufficient. It stores query and presentation settings, not materialized results. Dashboards and Boards may reference it, but each rendering rechecks source access. Unsaved chart edits remain local.
6. A department purge removes the department's dashboards and their widgets, as it removes the saved views of its modules. A widget in another department's dashboard that reads a purged module or field blocks the purge.

Boards are for communication. The Board scope decides who sees it; there is no audience on a post or an event, and there is no personal Board state:

1. There is one company Board. Every active account reads it; only administrators post and add events on it.
2. Each department has one Board. A Sandbox publish creates it for a new department and keeps its name equal to the department name; closing the department archives the Board and reopening restores it. The level on it is the department level ([`boards/access.py`](../../backend/app/systems/boards/access.py)); a user who reads only some modules of the department reads the Board. A department purge removes its Board and owned content, including published history, reminder work and notifications. Attached files must already have confirmed-purged bytes; references from other Boards still block source deletion. The [dependency inventory](../../backend/app/systems/sandbox/lifecycle/department_board_dependencies.py) and [lifecycle executor](../../backend/app/systems/sandbox/lifecycle/execution.py) include the owned graph in the locked, audited purge.
3. Administrators create project Boards and choose their groups in `board_groups`. The level on a project Board is the highest level of the user's groups there.
4. `read` shows posts and events. `write` adds posts and events and lets authors change, archive, and restore their own content ([`post_router.py`](../../backend/app/systems/boards/post_router.py), [`event_router.py`](../../backend/app/systems/boards/event_router.py)). `manage` also pins posts and manages other users' posts and events. A guest reads at most.
5. Each publish of a post adds an immutable revision; readers open earlier versions through `GET /api/boards/{id}/posts/{post_id}/revisions`. Deleting a post that was never published removes it; deleting a published post archives it. Only the Board purge removes revisions.
6. The author sets reminder timings (at the start, 15 minutes before, 1 day before) on an event. The worker queues one `scheduled_work` row for each reminder and occurrence and notifies current Board readers when it is due. A reminder may be delivered through and including 15 minutes after its due time; older reminders expire without delivery.
7. Publication and reminder notifications go to every account that can read the Board when they are delivered.

Lifecycle and audit behavior are application services. Audit captures ORM mutations in the same transaction as the domain change; Alembic and direct SQL are outside that capture boundary.
